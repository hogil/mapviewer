# 7K 다중 이미지 처리 최적화 기법 평가 결과

## 평가 개요

- **평가 일시**: 2025-11-13
- **테스트 환경**: 
  - 이미지 크기: 7788×7788 픽셀 (약 6,065만 픽셀)
  - 테스트 이미지: 10개
  - CPU 코어 수: 16개
- **평가 방식**: 3가지 방법 비교

## 평가 결과 요약

### 1. 현재 방식 (기존 코드)

- **전체 처리 시간**: 10.49초
- **이미지 로딩 시간**: 8.78초 (83.7%)
- **Sum Map 계산 시간**: 1.71초 (16.3%)
- **메모리 사용량**: 2,545.10 MB
- **특징**: 
  - 모든 이미지의 인덱스를 메모리에 저장 (`all_indices_list`)
  - `np.median`을 사용한 중앙값 계산
  - 정확한 카운트 제공

### 2. 비트마스크 방식 (제안 기법)

- **전체 처리 시간**: 3.02초 ⚡ **3.48배 빠름**
- **이미지 로딩 시간**: 1.97초 (65.2%)
- **LUT 생성 시간**: 0.00초 (무시 가능)
- **Sum Map 계산 시간**: 0.11초 (3.6%)
- **카운트 계산 시간**: 0.94초 (31.1%)
- **메모리 사용량**: 173.53 MB 💾 **93.2% 절감**
- **특징**:
  - `presence_map`: 각 픽셀에서 등장한 인덱스를 8비트 비트마스크로 저장
  - LUT(Lookup Table)를 사용한 중앙값 계산 (256개 패턴 사전 계산)
  - 메모리 사용량이 극도로 적음 (49MB + 오버헤드)
  - **한계**: 정확한 카운트를 제공하지 못함 (presence 여부만 확인 가능)

### 3. 하이브리드 방식 (비트마스크 + 정확한 카운트)

- **전체 처리 시간**: 8.82초 ⚡ **1.19배 빠름**
- **이미지 로딩 시간**: 8.73초 (99.0%)
- **LUT 생성 시간**: 0.00초
- **Sum Map 계산 시간**: 0.08초 (0.9%)
- **메모리 사용량**: 2,024.51 MB 💾 **20.5% 절감**
- **특징**:
  - 비트마스크로 presence 추적 + 별도 카운트 배열 유지
  - 정확한 카운트 제공
  - Sum Map 계산은 LUT 사용으로 빠름
  - 현재 방식보다 빠르지만 비트마스크 방식보다는 느림

## 상세 분석

### 성능 개선 요인

1. **비트마스크 방식의 우수성**:
   - 메모리 사용량: 2,545 MB → 173 MB (93.2% 절감)
   - 처리 속도: 10.49초 → 3.02초 (71.3% 개선)
   - 주요 원인:
     - `all_indices_list` 저장 불필요 (메모리 대폭 절감)
     - LUT 기반 중앙값 계산이 `np.median`보다 훨씬 빠름
     - 비트 OR 연산이 매우 가벼움

2. **LUT의 효과**:
   - LUT 생성 시간: 거의 0초 (256개 패턴 사전 계산)
   - Sum Map 계산: 1.71초 → 0.11초 (93.6% 개선)
   - 벡터화된 인덱싱: `lut[presence_map]` 한 줄로 완료

3. **하이브리드 방식의 타협점**:
   - 정확한 카운트를 제공하면서도 현재 방식보다 빠름
   - 메모리 사용량은 여전히 큼 (카운트 배열 유지 필요)
   - Sum Map 계산만 LUT 활용하여 부분적 최적화

### 메모리 사용량 비교

| 방식 | 메모리 사용량 | 주요 구성 요소 |
|------|--------------|----------------|
| 현재 방식 | 2,545 MB | `all_indices_list` (10개 × 49MB = 490MB), `counts` 배열 등 |
| 비트마스크 | 173 MB | `presence_map` (49MB), LUT (256 bytes) |
| 하이브리드 | 2,024 MB | `presence_map` (49MB), `counts` 배열 (1,920MB) |

- 카운트 계산: 0.94초 (31.1%)

## 결론 및 권장사항

### 1. 비트마스크 방식 (권장: Sum Map만 필요한 경우)

**장점**:
- ⚡ **3.48배 빠른 처리 속도**
- 💾 **93.2% 메모리 절감**
- LUT 기반 중앙값 계산이 매우 빠름
- 대용량 이미지 처리에 최적

**단점**:
- 정확한 카운트를 제공하지 못함 (presence 여부만 확인)
- 히트맵 생성 시 카운트가 필요한 경우 별도 처리 필요

**적용 시나리오**:
- Sum Map만 생성하는 경우
- 메모리가 제한적인 환경
- 대량의 이미지(100장 이상) 처리

### 2. 하이브리드 방식 (권장: 정확한 카운트가 필요한 경우)

**장점**:
- ⚡ **1.19배 빠른 처리 속도**
- 💾 **20.5% 메모리 절감**
- 정확한 카운트 제공
- Sum Map 계산은 LUT 활용으로 빠름

**단점**:
- 메모리 사용량이 여전히 큼
- 비트마스크 방식보다 느림

**적용 시나리오**:
- 히트맵 생성이 필요한 경우 (카운트 필요)
- 정확한 통계가 중요한 경우
- 메모리 여유가 있는 환경

### 3. 현재 방식

**장점**:
- 검증된 안정성
- 정확한 카운트 및 통계 제공

**단점**:
- 메모리 사용량이 큼
- 처리 속도가 느림

**적용 시나리오**:
- 기존 코드와의 호환성 유지가 중요한 경우
- 메모리와 속도가 크게 중요하지 않은 경우

## 추가 최적화 가능성

### 1. 스트리밍 처리
- 현재는 모든 이미지를 메모리에 올리지만, 스트리밍으로 처리하면 메모리 사용량을 더 줄일 수 있음
- 특히 100장 이상의 이미지 처리 시 효과적

### 2. 병렬 처리 최적화
- 이미지 로딩은 이미 병렬화되어 있음
- 비트마스크 연산도 병렬화 가능 (영역별 분할)

### 3. Numba JIT 컴파일
- LUT 생성이나 비트마스크 연산을 Numba로 컴파일하면 추가 성능 향상 가능
- 다만 NumPy 벡터화만으로도 충분히 빠름

### 4. 디스크 I/O 최적화
- 무압축 포맷(TIFF) 사용 시 디코딩 시간 단축
- 여러 파일을 하나로 묶어 연속 I/O 수행

## 실제 적용 시 고려사항

### 1. 카운트가 필요한 경우
- 비트마스크 방식만으로는 정확한 카운트 불가능
- 하이브리드 방식 사용 또는 별도 카운트 로직 필요

### 2. 메모리 제약
- 7K 이미지 100장 처리 시:
  - 현재 방식: ~25GB 메모리 필요
  - 비트마스크: ~173MB 메모리 필요
  - 하이브리드: ~20GB 메모리 필요

### 3. 웹앱 환경
- 비동기 처리 필수 (FastAPI 백그라운드 작업)
- 작업 큐 시스템 고려 (Celery 등)
- 진행 상황 모니터링 (SSE, WebSocket)
